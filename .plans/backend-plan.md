# smcli backend plan — remaining work

Shell-specific adapters around one shared backend. fff is for file search only, not history or
project understanding. Measure first; add machinery only when measurements justify it.

Status as of 2026-10-20: steps 1 to 7 are done on macOS arm64, and macOS x86_64 is verified (cross-built, service and
file-picker tests under Rosetta). Open: Linux (not supported), the smcli LICENSE and the xdiff (LGPL) decision, both
for the owner. The service is on by default; the schema is v7; `make test` and `make fresh` pass. The review fixes and
the built-in Potion model (`3822ac5`) improved existing code but are not plan steps.

Key finding from the baseline: at 100k runs, empty-prefix `suggest` (~450 ms) and picker first draw
(~700 ms) scan the whole history. Moving them into a service will not make them fast by itself;
the service must hold incremental state.

## 2. Persistent service — done

```text
Bash / Zsh / Fish adapters
          │
    smcli client / picker
          │ Unix-domain socket
          ▼
      smcli service
      ├── Existing command search + SQLite
      ├── Cached project context
      └── fff instances, opened lazily per root
```

- [x] Add a separate `smcli-service` executable target; thin clients must not link fff
  (shared code in the `SmcliCore` library)
- [x] Unix-domain socket in a user-private directory (0700); refuse other UIDs (check peer credentials)
  (one socket per database path, so `SMCLI_DB` users and tests never share a service)
- [x] Handle concurrent startup: lock file plus connect-or-spawn, losers connect to the winner
- [x] Protocol: versioned, newline-delimited JSON with `record`, `suggest`, `files`, `grep`, `select`
  (`files`/`grep`/`select` implemented in step 5; also `ping`, `shutdown`)
  - [x] Bound message size and request time; reject malformed requests with an error response
  - [x] Bound the number of active project/fff instances (LRU eviction): `FFFPool`, 4 instances (`SMCLI_FFF_MAX`),
    idle ones dropped after 600 s (`SMCLI_FFF_IDLE`); live instances listed in `ping`
- [x] Move ownership, not algorithms: wrap the existing `CapturedHistory` and `HistorySearch`
  - [x] `CapturedHistory`: one open connection; record and suggest
  - [x] `HistorySearch`: keep the engine, corpus and index open for `search` and the picker's Tab
    (`search` op; search code moved to the `SmcliSearch` library; the index is reopened when another process
    saves it); 100k runs: 860 ms → 28 ms warm, ~300 ms right after a record (corpus rebuild)
  - [x] Update the search corpus per record instead of rebuilding it (`commandStats` + native files, ~230 ms at 100k)
    (`CorpusState.add`; a test asserts it equals a rebuild from the database. 100k runs: search right after a service
    record 25.7 ms median, was a rebuild; after a write by another process it still rebuilds, now ~760 ms because it also
    reloads the `SuggestionIndex` that the ranking signals need. A changed native history file still forces a rebuild)
- [x] Hold incremental state in memory so `suggest` and the picker don't rescan all of history:
  per-command tallies updated on `record`, the corpus and index kept open
  - [x] `suggest`: `SuggestionIndex`, rebuilt only when another process writes (`PRAGMA data_version`);
    100k runs: 278 ms → 11 ms warm
  - [x] picker first draw through the service (`pick` op: suggestions + recent commands from `SuggestionIndex`;
    native history still read in-process, `commandStats` deferred to the first Tab); 100k runs: 680 ms → 64 ms warm
- [x] Idempotent records: client-generated event ID (store as `uuid`), ack only after COMMIT,
  duplicate IDs return the original ack
- [x] Fallback: if the service is unreachable, record directly and use the in-process picker
  (record, suggest, search and the picker)
- [x] Tests: concurrent shells, service restart mid-session, retry without duplicates, malformed input
  (`scripts/test-service.py`, `ServiceTests`)
- [x] Turn the service on by default once the step 3 shell tests cover it
  (unset = start as needed; `0`/`off`/`false`/`no` = in-process; `connect` = only use a running one;
  `make baseline`'s bench takes `--service on|off`, default off, and records which it measured)
- [x] Restart a service left running by an older build after an upgrade
  (every response carries `build` = real path|mtime|size of the service binary; a client that would spawn compares it with the
  binary it would launch, and shuts down + respawns on a mismatch or a missing field; `connect` clients never restart;
  protocol version unchanged; `scripts/test-service.py` covers a replaced binary and an old service without `build`)

**Done when:** concurrent shells work, restarting the service doesn't break the shell, and retries
don't duplicate history.

## 3. Native shell adapters — done

Existing: Bash (DEBUG/PROMPT_COMMAND/EXIT) and Zsh (preexec/precmd/zshexit) hooks; selections are
inserted, never executed.

- [x] Zsh: record `$pipestatus` alongside the exit status
  (schema v5 adds `commands.pipestatus`; `record` takes an optional 10th argument after the status, the 9- and 6-argument forms
  still work; the service `record` request has an optional `pipestatus`; Fish sends it too, Bash does not)
- [x] Zsh: verify composition with common plugins (oh-my-zsh, zsh-autosuggestions, atuin, fzf)
  (hooks are in `precmd_functions`/`preexec_functions`/`zshexit_functions` instead of wrapping `precmd()`/`zshexit()`, so later
  definitions can't displace them; tests simulate the plugins' hook, widget and keybinding patterns, none of them installed)
- [x] Bash: detect bash-preexec or `PS0` and prefer them over the DEBUG trap
  (bash-preexec -> PS0 on 4.4+ -> DEBUG trap; `SMCLI_BASH_HOOK=debug` forces the trap; an existing EXIT trap is chained)
- [x] Bash: keep the conservative fallback; verify `PROMPT_COMMAND` arrays (Bash 5.1+)
- [x] Fish: `fish_preexec`/`fish_postexec` capture, picker key bindings, `shell-init fish`
  (start times are whole seconds: fish has no clock builtin; the duration is fish's CMD_DURATION)
- [x] Fish: leave native autosuggestions alone
- [x] All shells: send cwd, shell/session ID, command, timing, exit info; no environment dump
- [x] All shells: honor user history exclusions (leading space always; zsh `HISTORY_IGNORE`; bash `HISTIGNORE` and
  `HISTCONTROL`; fish private mode and `fish_should_add_to_history`); preserve existing key bindings, traps and
  `PROMPT_COMMAND`; make extra key bindings opt-in
  (decision: Up and Ctrl-R stay on by default, since the picker is the feature, but a key another tool already bound is left alone
  and said so on stderr; Left-on-empty-line, Ctrl-Right and Alt-; moved behind `SMCLI_EXTRA_KEYS=1`; `SMCLI_NO_KEYS=1` unchanged.
  Limits: in PS0/bash-preexec mode Bash can't see the typed text, so with `ignorespace`/`HISTIGNORE` set an ignoredups duplicate is
  not recorded; zsh `zshaddhistory` hooks are not consulted)
- [x] All shells: insert selections into the command line, never execute them (keep this for Fish too)
- [x] Interactive tests in `scripts/test-shells.py`: multiline commands, Unicode, cancellation,
  repeated `eval` of the init, existing plugins, service down
  (bash 3.2 / 5.3 x {DEBUG, PS0, bash-preexec}, zsh, fish; the prompt carries a shell-incremented counter, so waits sync on the
  shell's own output, not the echo. The earlier hangs were the harness: started from a background job it passed an ignored SIGINT
  to every shell, so Ctrl-C never stopped `sleep`; and two scenarios asserted the wrong hook layout. `SMCLI_TEST_ONLY=<label
  substring>` narrows a run)

**Done when:** those interactive tests pass for Bash, Zsh and Fish.

Later, only if measurements justify it: persistent Zsh socket transport, async suggestions.
Not planned: TCP listener, Bash loadable builtin.

## 4. Cached directory context — done

- [x] Repository/worktree: discover with Git's rules (`.git` may be a file); shared repo identity,
  current worktree, branch, operation state (merge/rebase)
  (`ProjectContext.discover`, `Sources/SmcliCore/DirectoryContext.swift`; commondir = identity; markers for
  merge/rebase/am/cherry-pick/revert/bisect; paths are real paths)
- [x] Project/package: nearest manifest (Package.swift, package.json, Cargo.toml, pyproject.toml,
  go.mod, Makefile); support nested packages
  (nearest first, then enclosing ones up to the repo root; outside Git only the nearest)
- [x] Directory: cwd relative to the repo and project roots
- [x] Read manifests declaratively only (project type, package-manager hints, script names);
  never execute manifests or task files
  (text/JSON parsing only; package.json scripts, Makefile targets, Cargo bins, pyproject scripts, Package.swift
  targets by regex; lockfile/`packageManager` hints)
- [x] Refresh Git status asynchronously; serve cached context while refreshing
  (`ContextCache`; `context` op is served off the state queue, returns `statusPending`; `smcli context` waits up to
  0.5 s for a first status)
- [x] Invalidate on filesystem events plus a bounded freshness check (`.git/index` timestamps alone
  miss working-tree changes)
  (FSEvents on the worktree plus git/common dirs; 5 s max age; refreshes >= 1 s apart; 16 worktrees max, LRU.
  macOS only, other platforms rely on the age check)
- [x] Get Git state from structured Git output (e.g. `git status --porcelain=v2`), not prompt output
  (`git status --porcelain=v2 --branch` via `/usr/bin/env git`, no shell, `GIT_OPTIONAL_LOCKS=0`, 10 s timeout)
- [x] Tests: nested projects, worktrees, branch switch, unstaged edits, non-Git directories,
  with no blocking on the typing path
  (`Tests/smcliTests/ContextTests.swift`, `scripts/test-service.py`; CLI: `smcli context [--json] [--dir D]`)
  Warm `smcli context` on this repo: ~11 ms via service, ~23 ms in-process (process start alone ~9 ms)

**Done when:** those cases produce correct context without blocking typing.

## 6. Incremental ranking signals — done

Existing: same-directory boost, recency (two-week half-life), success rate (Ctrl-C and `grep`-style
exit 1 aren't failures), relevance-scaled usage boost, and a "why" per result.

Measured with `make ranking` (`RankingQualityTests`): a deterministic synthetic history over real temp directories
(manifests, `.git` markers), 16 suggest and 11 search queries with an expected top result, scored by MRR and top-1/top-3
(search runs the real potion model). It fails below a floor (suggest MRR 0.95 / top-1 0.90, search 0.90 / 0.85).
`SMCLI_RANKING_OFF=project,transition,selection,script,hint` switches signals off to measure each one.

| signals on (cumulative)     | suggest MRR / top-1 | search MRR / top-1 |
|-----------------------------|---------------------|--------------------|
| none (baseline)             | 0.510 / 0.38        | 0.452 / 0.27       |
| + project                   | 0.552 / 0.44        | 0.513 / 0.36       |
| + selection feedback        | 0.624 / 0.56        | 0.591 / 0.45       |
| + transitions               | 0.719 / 0.69        | 0.636 / 0.55       |
| + project scripts           | 0.875 / 0.88        | 0.818 / 0.73       |
| + Git-state hints           | 1.000 / 1.00        | 0.955 / 0.91       |

The fixture is small and I tuned weights against it, so the absolute numbers flatter; the one search miss left
(`swift test` in a package: a sibling-directory habit ranks second to a more frequent unrelated `swift test --parallel`)
is kept as an honest failure. Latency at 100k runs through the service (`bench-baseline.py --service on`, 5 samples):
suggest 13.2 ms warm (was ~11), picker first draw 62 ms (was 64), search 24 to 26 ms (was 28).

- [x] Build a fixed query set with expected top results; score the ranking (e.g. MRR) before each change
- [x] Same project/package boost (needs step 4)
  (derived at query time from the nearest manifest root, no stored column: suggest weights runs there x3, between
  the query directory x4 and above/below x2; search counts `runsProject` from `commandStats(project:)`)
- [x] Query -> selection feedback from `select`
  (`select` with `mode` suggest or search and a `command`; table `command_selections`, schema version 7; the picker
  reports the pick, in-process when there is no service; picks fade with the two-week half-life and match by query
  similarity, a repeated query most; purged by `prune`)
- [x] Previous-command affinity (command transitions)
  (counts of what followed what within a session, kept by `SuggestionIndex` and updated per record; the shell adapters
  export `SMCLI_SESSION` so the picker, `suggest` and `search` can name the session; the scan uses `LAG()` in SQL)
- [x] Project-provided scripts and validated targets as candidates
  (`ProjectContext.candidates()`: package.json scripts, Makefile targets, Cargo bins, pyproject scripts, Package.swift
  targets; only names present in the manifest and only plain identifiers; nothing executed. Unrun ones enter suggest at
  a low score and search only when the query's words match them)
- [x] Git-state hints (e.g. mid-rebase -> `git rebase --continue`)
  (rebase/merge/cherry-pick/revert/am/bisect from the Git directory markers; pinned above the best score, only where
  the typed prefix allows)
- [x] Keep embeddings separate from mutable usage/context metadata; don't force semantic
  results through a lexical filter
  (checked: `searchDocument` takes only command and intent, a test pins that usage and context fields don't change it;
  retrieval is never filtered by keywords, the only filter is `SearchFilter`; lexical matching is used solely to admit
  extra project candidates and picked commands to the rerank pool)
- [x] Add each new signal to the "why" output
  (search results and, new, `Suggestion.why` in `suggest --json`: used here / in this project, often follows X,
  picked for similar searches, package.json script, rebase in progress...)

**Done when:** the fixed query set ranks better with acceptable latency.
